## Rules

- **A repeated `MutationId` is a no-op that returns the prior row.** This holds for `RecordStore::create_job`, `retry_job`, `cancel_job`, `record_artifact`, `insert_review` and `insert_receipt` (when it is given one), `WorkspaceCatalog::create`, `update` and `archive`, `ConfirmationStore::create`, `DraftStore::save` and `discard` (keyed with the item), `ProposalStore::insert` and `add_comment`, `UploadStore::create`, and `CredentialStore::create_connector`, which answers `ConnectorIssue::Existing` and never a second secret. Enforce it with a unique column, not a lookup. There are no `find_*_by_mutation` methods.
- **The mutation ledger leases by token and keeps finished rows 7 days.** The key is (tenant, subject, client, operation, idempotency key). `MutationStore::begin` grants a `MutationLease { mutation_id, token }`, and every grant of the same mutation carries a token no earlier grant carried. `complete` is a compare-and-set on that token: it fails with `Conflict` and stores nothing when the lease is no longer the current grant (it expired and another attempt holds the mutation). `release` ends the lease only for the current grant; under a stale lease it changes nothing. Completed, released and terminally purged rows are kept 7 days from their existing finish clock; a row whose lease expired without `complete` or `release` stays until it is reconciled by a later attempt or a recorded workspace purge. `complete` returns `Conflict` only for a lost lease (other failures use `Unavailable` or `Internal`). `begin` also returns `Conflict` for an existing terminally purged row, or a released or expired leased row whose workspace has a recorded purge, except for the purge operations; this does not apply to every existing completed row. Releasing a completed or terminally purged mutation is a no-op. Construction gates: `mutation-lease-compare-and-set` (a superseded attempt can neither complete nor release; both takeover orders) beside `mutation-crash-reconcile`. The lease length is the storage lane's choice: a mutation lease lasts 120 seconds (`mutations::MUTATION_LEASE_SECONDS`), and a job claim 300 seconds (`records::JOB_LEASE_SECONDS`), renewed by `update_progress`.
- **Each ledger row records its mutation's workspace, and a purge reads only that.** `mutations.workspace_id` (records schema V2) is the first `begin`'s workspace (the request's first target) or, while `NULL`, the workspace a tenant-level completion names at `RequestScope::RESPONSE_WORKSPACE`; response text is never searched. For non-purge operations, `complete`/`release` check a recorded workspace purge in the same transaction and write terminal state `purged` without digest or response instead of `completed`/`released`. `begin` refuses an existing `purged` row before digest comparison; a released or expired leased row of a recorded purged workspace becomes `purged` before the refusal commits. Those retries never resume the handler or move an existing retention clock; ordinary completed rows retain replay semantics. The key, `MutationId`, workspace and lease token remain; `purge_workspace`/`purge_item` and other workspaces retain ordinary replay. Lifecycle ruling9 establishes that no installation predates records schema2; the one pre-V5 records copy is sanitized before upgrading. The `purge::rows` rewrite terminalizes existing completed/released rows in schema 5; older copies are released with empty digest and NULL response. Required ledger columns are validated before any table is changed; malformed copies stop the purge.
- **`VersionStore::commit` is idempotent on `MutationId`.** Every commit carries an `Okf-Jawn-Mutation:` trailer. Before writing, scan `expected_head..head`; a commit with the trailer is returned with `replayed: true`. `mutation-crash-reconcile` proves it: the commit succeeds, `MutationStore::complete` is never written, the retry calls `commit` again with the same id and gets the first revision back; no second commit exists. `find_commit` exists only for a writer whose expected head is not stable across attempts (a Snapshot, an import's commits, a restore).
- **A replay answers the warnings that commit was given, or says they are unavailable; never another attempt's.** `commit` writes the check's warnings (an empty list too) to `commit_warnings` (records schema V3), keyed by workspace and mutation and naming the commit they were kept for (`commit_id`), after the check and before the reference moves; `promote_candidate` writes the empty list. A replay, by `commit`, `promote_candidate` or `find_commit`, answers that row only when the row names the commit that was found. No row, a row kept for another commit, or a row that does not read, answers the one warning `core::storage::replay_warnings_unavailable` and never an error. A row without a commit (a crash in between) is replaced by the next attempt, commit and warnings together; the same replacement means a later attempt that checked and then could not land leaves the landed commit of its mutation answered as unavailable. Only the workspace's purge removes the rows; a workspace archive carries none.
- **A job sealed past its point of no return refuses its cancellation while it is queued or running; the seal survives lease expiry and retry.** `jobs.sealed` (records schema V4) is set by `RecordStore::seal` only under the job's current, unexpired claim of a running job; a job already cancelled is answered as it is and stays unsealed, so the store orders the seal and a cancellation and only the first takes effect. `cancel_job` refuses a sealed queued or running job with `Conflict` inside the cancel's transaction, keeping no control row. `expire_leases` and `retry_job` leave the seal as it is, because the attempt that runs the job next resumes the same work. A sealed job may still fail (`fail_job`) and be retried; only its cancellation is refused. A records database upgraded from schema 3 has every job unsealed, after a pre-migration copy. The wire `Job` does not show the seal.
- **Stage, check, then commit.** `commit` and `create_candidate` materialize the base tree in `<data>/staging/<tenant>/<workspace>/<mutation>`, apply the `TreeEdit`s there with `okf-core` (moves, link rewrites, index regeneration), call the `CandidateCheck` they were given on that directory, and only then write the tree and the commit and move the reference. The check is told `rewritten`: the files the store rewrote while it applied the commit's edits (the referrers of every move, as the tree spells their paths, in path order, each once, without a moved item's own two paths and without a file that is gone from the candidate). A file rewritten and then rewritten back is named. Remove the directory when the call returns, success or failure; remove anything a crash left under `<data>/staging` at startup. Never decide OKF conformance here: that is the check's job, and the check is core's.
- **No selectors, identities or wire requests.** Ports take a `StorageScope` or `TenantId`, resolved `Revision`s and core parameter types. `WorkspaceCatalog` never filters and returns `Workspace::permissions` empty.
- **Hashes are defined in core.** Store and look up connector secrets with `core::credentials::secret_hash`; sandbox tokens arrive already hashed with `core::sandbox::token_hash`. Never store a plaintext secret or token.
- **Bytes have no media type.** `BlobStore` keys objects by tenant and SHA-256; the media type lives on the source card, the asset or the sandbox capability that refers to the object.
- **An artifact is a record over a blob.** Export, backup and View-export bytes are retained in `BlobStore` like any other object; `RecordStore::record_artifact` maps an `ArtifactId` to `{ kind, digest, size, media type, producing job }` and `get_artifact` reads it back inside one workspace. `Job.artifact` is `ArtifactRecord::download` of that record. Artifact rows are application records: a backup includes them and rebuilding search never touches them.
- **Drafts are never indexed, exported or committed implicitly.** `SearchIndex` reads committed trees only.

ingest owns `JobHandler(&ClaimedJob)` and the Tokio runtime adapter; storage owns the durable stores those handlers write through, and returns the `JobSpec`, initiator and `MutationId` it was given, unchanged, on every claim.
