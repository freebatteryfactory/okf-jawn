## Phase 1: the design (write core-m1-3b-design.md in the README directory, then return DESIGN)
For each field of `NamingRule`, in the order a name is built, state exactly what it does, as a numbered algorithm a reader could implement from, and give at least four test vectors (input path, type, rules, expected output or refusal), the hard cases among them. At least:
- **Which items a rule applies to.** `glob` against the workspace path (forward slashes, as the tree spells it; is matching case-sensitive; what `*`, `**`, `?`, `[...]` and a leading `/` mean; a glob that matches nothing; a glob that is not valid is refused at `set_rules` with its field). `type_name` (absent: any type). Rules in list order: the FIRST matching rule names an item, or every matching rule applies in turn (choose, and say why).
- **The base name** (the file name without its extension): `strip_version_suffix` (which suffixes are "version suffixes": `v2`, `-v2`, `_final`, ` (1)`, `-copy`? state the exact list or pattern), dates (`date_order` reads a date in the name: which spellings are recognised; `reject_ambiguous` and an ambiguous date such as `03-04-2025` produce a warning on that entry and leave the name unchanged, never a guess (SPEC section 6); `date_format` writes it: name the syntax a person writes in the YAML and the form, keep it small and printable, and refuse an invalid one at `set_rules`), `case` (how words are split: spaces, separators, camelCase, digits; what `title` does with an acronym, with `iPhone`, with a non-ASCII letter), `separator` (which characters are word breaks; a separator that is not allowed in a path segment is refused at `set_rules`), `prefix` and `suffix` (applied once; a name that already has them is not prefixed twice).
- **The extension** (`extension_policy`), never applied to an original (a source's original file keeps its name exactly: SPEC section 6 "Preserve originals").
- **The folder** (`destination`): the template syntax (which placeholders: the type, parts of the date, the original folder?), how a placeholder with no value is handled, and that the result must be a `WorkspacePath` (Windows-reserved segments, NFC, at most 4,096 bytes: an entry whose result is not one gets a warning and no rename).
- **Aliases** (`alias_preservation`): what is kept, where (a frontmatter key? which one? OKF's own alias property if it has one: read okf-core), and that the links the move rewrites are what keeps references working.
- **Collisions** (`collision`): with existing items and with other entries of the same plan, compared by `collision_key` (case and normalization); `reject` (the entry is refused, the plan says so), `suffix` (the exact suffix form: `-2`, `-3`, in what order the plan assigns them so that it is deterministic), `keep_existing`. Every pair that collides is a `DuplicateObservation`.
- **What stays**: archived items are never renamed (counted in `archived_left_out`); a source card's name follows `source_card_name` and the rules apply on top (say exactly how); the reserved files (`index.md`, `log.md`, anything under `.okf/`) are never renamed; an item whose name would not change is `unchanged`, not an entry.
- **Determinism**: the same rules and the same tree give byte-identical plans (order of entries; of observations); the plan's `rules_digest` is SHA-256 of the canonical JSON of the rules.
- **`set_rules` validation**: every refusal, with its field as a JSON Pointer (`/rules/rules/2/glob`).
- **`get_rules`**: the answer with no rules saved (`rules` absent), with an unreadable file (`unreadable` with the text and each problem located at its line where the YAML reader gives one), and with a `schema_version` this build does not know.
- **`apply_names`**: how the plan is revalidated against the current state (the plan's `base_revision` must be the head: `conflict` with `StaleBase` otherwise; the rules' digest must equal `rules_digest`; every entry is recomputed and must equal the plan's, or the whole apply is refused: SPEC section 6 "A stale preview must not silently apply"); the moves are ONE commit with the links rewritten (`MoveItem` for each, through the same path every move takes, so the rewritten referrers are told to the check); what a plan too large for one request does.
- **The shared function for import (R-I4)**: its signature (rules, a proposed path and type, the collision keys already taken, including those of the cards the same import writes) and that `preview_names` and the import call it, so the two cannot differ. Ingest's import today refuses `apply_naming_rules: true` with `not_implemented` (request R-I4): phase 2 wires it.
- **Libraries.** For glob matching, case conversion and dates: what is already a dependency of core (`time` is; `heck` and `glob` are in Cargo.lock only as other crates' dependencies), what each candidate does with the cases above (read the installed source under the cargo registry; quote the function and its behaviour), and your proposal, with versions. A homegrown matcher is not allowed (AGENTS.md: no homegrown parser). The integration owner makes the manifest change and the vendor notes; you do not touch a manifest.
- **What is open**: anything a person would reasonably disagree with (product taste: for example what title case does to "iPhone") listed separately, each with your proposal, so the integration owner can put it to the owner.

Return `DESIGN` with the path of the design file and the list of open questions. Do not start phase 2 until you are told.
